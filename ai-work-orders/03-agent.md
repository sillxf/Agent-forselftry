# 任务 03：告警调查 Agent 证据链与可回放输出

## 轮次状态

启动时先读 `ai-work-orders/workspace/CURRENT.md`。`status: implementation` 才执行本任务的代码修改；`status: acceptance` 时只基于当前对话已有工作和可访问差异补齐执行报告，不得继续开发。若历史成果或差异不可访问，如实说明，不要编造。

## 目标

完善现有安全告警调查 Agent，使其每个关键判断能回到告警/工具观察/RAG 证据，能诊断检索与生成分别发生了什么，并可将一次调查输出作为可追溯运行记录。保持代码拥有控制权、模型只做有界选择与报告生成；不把原型强行改造成多 Agent 平台。

## 当前基础

正式告警入口是 `python -m agent`，核心为 `agent/investigator.py` 的单节点有界循环；状态、调用步骤、预算在 `agent/state.py`，只读工具在 `agent/tools.py`，来源校验在 `agent/verify.py`，RAG 客户端在 `agent/knowledge.py`。Agent 不应直接读 RAG 数据库、原始文件或索引。

仓库还有 `agent/demo.py` 的 DesignAdvisor 演示流程。它是不同用途的设计顾问，不是告警调查入口；不得把两者混称为同一 Agent 质量结果。

## 范围

仅修改 `agent/` 下文件。先读项目及 Agent README、入口、RAG client、工具、状态、报告 schema 与测试。优先聚焦正式告警调查主链路，而非给 demo 增加新功能。

1. 对每次初始和后续 RAG 搜索，尽可能通过 REST 请求 `include_trace=true`，并在 Agent 运行结果中记录可追踪的 request ID、generation、配置 revision、引用信息和服务提供的检索 trace。若服务未提供 trace，明确标记 `unavailable`，不可据此伪造空结果。
2. 将一次调查的步骤记录做成可回放的结构化输出：输入告警的稳定 ID/hash、规则风险、工具名称/调用 ID/安全参数摘要/状态/耗时、模型调用序号与用量、RAG request/generation/evidence IDs、报告校验/降级结果、终态与失败类别。原始告警及证据文本只按当前输出策略处理；不记录凭据、Authorization header 或不必要的个人/敏感信息。
3. 明确观测与知识证据的区分。引用校验继续保证 source ID 属于本次 run；不能仅因引用 ID 存在就宣称语义蕴含已被证明。在输出中保留报告降级、未知来源、状态调整及校验规则版本。
4. 检查初始 RAG 检索和工具检索的空结果、低相关结果、服务未发布、超时、限流、权限拒绝与索引损坏如何区分；失败不得伪装成“未发现攻击”。避免未经评测就硬编码跨模型通用的 relevance 阈值。
5. 保留确定性的代码控制：工具白名单、参数 schema、只读权限、最大 LLM/tool/search 次数、重复调用限制、final turn 和服务端报告 schema 校验。明确现有工具只在调用者提供的告警批次内关联，不宣称接通真实 SIEM/资产/身份日志。
6. 检查模型返回多个工具调用、非法参数、超时及报告格式错误时，步骤状态和计数一致；错误对用户可用且不泄露 provider 密钥/内部请求头。
7. 使用已有 CLI JSON 输出或最小兼容选项导出记录；不要为了“可回放”直接引入队列、数据库、SSE 或多 Agent 编排。需要跨重启任务恢复时，应将其列为后续架构决策，而不是假装已支持。
8. 为上述改动增补确定性 Agent 测试，并说明如何通过现有 benchmark 运行评估；不要修改 benchmark 数据或评测代码。

## 共享边界

- 只通过 `RAGKnowledge` 的 REST API 使用知识。禁止从 Agent 导入 RAG 检索、存储或索引内部类。
- 使用现有 `POST /api/v1/search` 字段。`include_trace`、`request_id`、`generation_id` 和证据引用按可选/缺失情况健壮处理。
- 不改变 RAG API 契约；发现缺少必要字段时，在结果报告中向 RAG 负责人提出兼容性建议。
- 不改 `RAG/`、`benchmark/` 或根配置。不要把 `.env`、模型密钥或真实敏感日志写入工作区或提交。

## 非目标

- 不拆成多 Agent，不增加自主规划框架，也不引入长期记忆。
- 不执行封禁 IP、禁用账户、隔离主机等有副作用操作；当前建议仅作为未执行提议。
- 不声称系统支持任务暂停、取消或跨进程断点续跑；当前 CLI 单次调查结束后保存结果不等于任务恢复。
- 不把“引用存在”包装成自然语言结论与证据蕴含完全一致。
- 不让 Agent 直连 SIEM/资产数据库；数据源连接需独立契约与权限设计。

## 实施步骤

1. 画出当前正式入口的实际调用链，并指出现有输出已有和缺失的可观测字段。
2. 实施兼容性最小的 trace 采集和结构化调查轨迹，保持现有报告格式兼容。
3. 审查工具/模型异常状态分类、预算和多工具调用处理，只修改证据明确存在的缺陷。
4. 为改动路径增加 `agent/tests/` 确定性用例；运行 Agent 对应测试，报告命令和结果。
5. 更新 `agent/README.md`，明确 RAG 依赖、告警批次边界、报告证据类型和任务恢复限制。

## 验收标准

- 对一次成功调查，可从最终输出找到每条工具调用与结果、知识检索 request ID/generation、证据引用和最终报告校验结果；没有 trace 时状态明确。
- timeout、not_published、index_damaged、not_authorized、busy 和真正的 empty 结果保持不同语义；服务异常不变成“没有相关证据”。
- 未知或错误 source ID 仍被剔除/降级并可追踪；引用 ID 合法不代表其内容蕴含结论，文档和输出不会夸大校验强度。
- 工具权限只读、预算和重复调用防护不被削弱；模型不能通过 tool 参数改变调用者身份或知识库授权范围。
- 不泄露密钥；现有 CLI 使用方式和 JSON 报告消费者保持兼容，新增输出字段采取向后兼容策略。
- 相关 `agent/tests/` 测试通过；未运行全仓测试时说明原因。没有触发模型付费 live benchmark。
- 文档诚实说明当前是单次调查/批次工具流程，不是持久化异步任务平台。
