# 任务 01：Benchmark 自动生成、机器质检与 AI 裁决

## 轮次状态

启动时先读 `ai-work-orders/workspace/CURRENT.md`。`status: implementation` 才执行本任务的代码修改；`status: acceptance` 时只基于当前对话已有工作和可访问差异补齐执行报告，不得继续开发。若历史成果或差异不可访问，如实说明，不要编造。

## 目标

在不要求用户逐题人工审核的前提下，把现有安全 RAG/Agent 候选数据改造成**可自动运行、来源可追溯、能暴露不确定性的机器裁决 benchmark**。目标不是把 AI 判断伪装成人工真值，而是让机器质量控制透明、可重复，并将低置信或裁决冲突样本从主指标中隔离。

## 背景与问题

当前 `benchmark/datasets/security-v1/` 有 100 道 RAG 候选题，`benchmark/evaluation/agent/cases.jsonl` 有 12 个合成调查案例。它们目前不是人工审核集。答案评测的词面评分很粗；Agent 评测运行器默认最多 8 个案例，但现有案例有 12 个，README 的完整运行示例没有指定子集，可能超限退出。现有分块实验有基于 `query_family` 的稳定拆分，可作为起点，不要丢弃其防止近似题跨集合泄漏的意图。

## 范围

仅修改 `benchmark/` 下文件。需要先读当前数据格式、manifest、评测器、实验入口和 README，再基于当前代码实施，不要另起一套并行系统。

1. 定义版本化、机器可处理的数据契约，至少区分：来源与精确证据锚点、问题/任务、可回答性、必要事实、可接受替代表达、禁止结论、期望工具行为（Agent）、难度/类别、query family、拆分、标注来源、机器校验状态、裁决置信度与不确定原因。
2. 用确定性程序校验 JSONL/schema、来源文件哈希、证据引用定位、ID 唯一性、字段完整性、split 泄漏和必需/禁止字段互斥等。
3. 为需要语义判断的标签提供显式 opt-in 的 AI 裁决器：至少做两个相互独立的判断（优先不同模型/供应商；若当前配置只能调用一个模型，使用隔离的独立评审轮次并明确标记相关性限制）；只有有分歧时才做第三次裁决。设单题请求上限和整个运行预算上限，支持断点续跑，禁止把密钥写入运行结果。
4. 裁决应以固定来源文档和证据片段为依据。要求结构化输出：每个关键标签、证据定位、置信度、分歧和裁决理由。低置信度、证据不存在、相互矛盾、无法解析的项目标记为 `unresolved` 并排除出主质量分，不静默猜测。
5. 明确机器状态字段，例如 `machine_status` / `machine_review`；不得将机器通过写成 `review_status=approved` 或声称人类审核。汇总至少分别报告总样本、机器通过、未决、AI 一致率、裁决率和排除数。
6. 区分开发/回归/最终留出集。按 `query_family` 或等价语义族分组后稳定拆分；保留拆分盐值/算法版本。留出集不得用于参数选择，报告要说明仓库内数据不是密码学意义上的隐藏集。
7. 评测分层：检索层指标与逐证据命中；答案层事实覆盖、禁止事实、引用有效性和拒答；Agent 层工具选择、证据类别区分、越权/注入抵抗、空结果与失败处理、格式与预算。词面规则只能作为确定性子指标，不能单独宣称语义正确。
8. 修复 Agent 评测默认案例数量与 CLI 文档不匹配问题；dry-run 应能验证实际会运行哪些案例，而不调用付费模型。
9. 输出每次运行的机器可读 JSON 报告，包含数据版本及 hash、代码提交、评测器和 prompt 版本、模型标识、运行时间、预算、拆分、分层指标、置信区间/样本量提示、未决项目和限制。不可记录凭据或未脱敏业务数据。

## 设计约束

- 不要求人工逐题审核或人工逐条确认；不提供“等待人工批准才完成”的阻塞流程。
- 不可制造没有来源的 ground truth，也不可通过让生成器与评判器共享答案提示来虚增一致率。
- 数据生成、数据校验与被测系统应尽量隔离；生成模型不能直接看到最终评分标准中的全部答案线索后再生成同题。
- 若没有第二个可配置模型，不得假称有多模型独立裁决；应在报告中写明降级方式。
- 限制在线请求费用；网络/模型运行必须有明确 CLI 开关和最大请求数。离线 schema、哈希与契约检查不应需要模型。
- 不改 `agent/`、`RAG/` 或根级运行逻辑。若发现接口缺陷，记录建议，不直接越界修复。

## 非目标

- 不承诺 AI 裁决等价于专家真值或真实生产事故表现。
- 不建设通用众包/人工标注平台。
- 不以增加题目数量替代代表性、难度控制和可靠性分析。
- 不把小样本候选集宣传为统计显著的性能结论。

## 实施步骤

1. 检查现有 schema、数据来源、评测命令和运行产物；列出可复用组件及兼容迁移策略。
2. 先实现版本化契约、确定性校验和稳定拆分，并为当前数据生成不冒充人工审核的机器状态。
3. 实现预算受限、可恢复的 AI 评审/分歧裁决；隔离生成器和评判器上下文。
4. 将各评测层的结果汇总到同一机器可读报告，并修正 CLI 的默认行为和说明。
5. 补足与变更路径直接相关的离线测试；不运行付费 live 评估，除非用户之后明确指定预算与模型。

## 验收标准

- `python -m unittest discover -s benchmark/tests -p "test_*.py"` 通过；若改动涉及其他 benchmark 测试，报告运行了哪些对应测试。
- 离线校验能检出错误哈希、无效证据锚点、重复 ID、字段错误和 query family 泄漏。
- dry-run 不访问模型；live 模式必须显式开启并强制请求/成本上限。
- 评审结果可断点续跑且不重复计费已完成样本；相同输入、版本、配置的报告可追溯。
- 输出明确区分 `machine_validated`、`unresolved` 等机器状态与人工审核；当前无人审核的样本数量在报告中一目了然。
- 未决和低置信样本不会被当作正确答案纳入主质量分；同时显示其比例，避免通过排除难题美化指标。
- Agent 评测 README 中提供的默认命令对当前案例数有效，或者明确要求显式选子集并提供对应示例。
- 最终报告明确限制：自动裁决不是人类 ground truth；小样本和候选数据不能证明生产质量。

## 交付报告

列出修改文件、数据契约/版本变化、AI 裁决策略与预算、指标和排除规则、运行命令与结果、未决比例、已知偏差/风险。不要只报一个总分。

完整报告必须写入 `workspace/CURRENT.md` 中 `benchmark_report` 指定的共享路径，使用 `workspace/templates/execution-report.md` 作为补充格式。即使代码在独立 worktree 中修改，也要将报告写入主项目共享工作区；对话回复只需简述结论和报告路径。不得覆盖其他角色的报告。
