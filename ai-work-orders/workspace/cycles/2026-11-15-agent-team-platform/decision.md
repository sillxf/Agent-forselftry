# Architect 决策：可组合的 AI 团队与角色库

## 当前产品问题

项目发起人可以使用优秀的 coding AI，但仍要自行探索应该如何做项目、寻找工程资料、划分职责、创建多个对话、搬运上下文、交接产物和检查结果。目标产品要降低这种探索与协调成本，让用户能组织自己的 AI 团队，让团队成员通过专业化角色定义、项目知识和受控工具完成有实际意义的工作。

产品价值不等于“多个 AI 对话”或“堆叠 RAG、Agent、A2A 等技术名词”。需要演示完整工作过程：团队接收目标，制定有界计划，成员自主选择获准工具，根据工具反馈继续或调整，交付产物，并能检查过程和失败情况。

## 本轮目标与阶段

本轮只要求协调 AI 基于仓库现状形成完整、可执行的分阶段落实方案。不得直接修改产品代码或把方案当作开发授权。方案需说明如何从当前仓库演进、复用现有 RAG 的边界、最小可用版本、后续扩展路径和明确的非目标。

## 推荐产品范围

### 首版需要支持

1. 用户可导入、查看、保存、导出和选择角色包。
2. 用户可以从角色包创建项目内的角色实例，并把一个或多个成员组合成可保存的团队。
3. 一个协调者可围绕用户目标形成有限计划，将任务交给团队成员；成员能调用授权工具、读取反馈、在边界内继续工作，并交付明确产物。
4. 用户能查看运行阶段、角色任务、工具调用状态、结果、交接、失败与最终产物；运行记录可追溯。
5. 首个演示只需一个导入的自定义角色加系统内置协调者，验证角色导入、团队实例化、工具使用、反馈后继续/调整和产物交付的完整闭环。之后才扩展为任意多个本地角色。

### 明确不属于本轮产品责任

- 不开发“自动创建专家角色”的产品功能。
- 不认证、评级或保证导入角色的领域专业水平；不要求建立角色专业能力 benchmark。
- 角色包格式、安全和兼容性检查属于产品责任，但这不等于专业能力验证。
- 不在首版建立角色市场、社区审核体系或自动角色优化平台。
- 不在首版连接远程托管 Agent，不立即实现 A2A。
- 不建设通用知识图谱或承诺 RAG 对任意资料/问题都能检索正确。
- 不允许 Agent 无限制互聊、无限派生任务或无预算运行。
- 首版默认只读工具；写文件、提交、部署、发信、创建工单等副作用操作需要独立授权/确认策略。

## 关键架构决策与要求

### 1. 角色包与角色实例分离

角色包是可移植、版本化的定义；角色实例是该定义在某个项目/团队中的配置，拥有独立的模型选择、项目资料范围和工具授权。一次运行应固定角色包版本和团队配置快照，更新包不得静默改变进行中的运行。

首版角色包可采用受限 ZIP/目录格式，至少包含 manifest、角色指令和可选输入/输出契约、参考资料清单。格式、大小、路径、版本和兼容性需要校验。首版导入内容视为不可信数据，不自动运行脚本或安装依赖。不得将用户密钥、provider 凭据、私有项目资料或默认权限放入可分享包中。

### 2. 团队配置与团队运行分离

可保存的 Team Definition 描述成员、职责实例及必要的任务路由/边界；Team Run 保存一次任务的实际状态、执行事件和产物。角色包、团队模板、运行实例不能混成同一种记录。

### 3. 协作以有界任务和产物为中心

成员交接应是结构化任务和产物，不以无限自由聊天作为主要协议。每个任务需要有负责人、输入资料、允许工具、完成条件、状态、期限/预算及交付格式。协调者可以基于反馈动态选择下一步，但需要最大步骤数、最大并发数、最大委派深度、时间/模型预算、重试次数和停止/升级条件。若选择更简单的静态 DAG 或受限动态编排，请在计划中比较后给出推荐及理由。

### 4. 工具权限由系统强制执行

角色声明需要的工具不等于获得权限。权限由用户/团队实例授予，按项目和操作范围隔离；凭据由连接器安全管理，不进入角色包或模型提示。工具需要 schema 校验、超时、调用 ID、错误分类、重试/幂等策略。首版优先使用现有 RAG REST API 与最少的只读项目工具，避免扩大到真实企业系统集成。

### 5. RAG 是可选知识连接器，不是产品中心

角色可按权限调用现有 RAG REST 服务和项目资料工具。检索证据需要保留来源、版本/代次（可获得时）、引用和请求追踪；“引用存在”不得被描述为结论已被语义证明。角色需要整章或原文上下文时，应在计划中评估现有 API 能力和最小补充，而不是默认加知识图谱或重建 RAG。

### 6. 运行状态和过程记录是首版核心能力

计划方案应定义最小实体与持久化模型，至少分析 role package/version、role instance、team definition/member、run、task、event、tool call、artifact、permission grant 之间的职责和关联。运行过程要能表示 queued/running/waiting-user/paused/failed/cancelled/completed 或等价状态，并区分空结果、工具失败、超时、权限拒绝和部分完成。

可追溯记录至少需关联 run ID、任务/事件 ID、角色包版本/hash、团队配置快照、模型/提示配置标识、工具调用与结果状态、RAG request/generation/citation（适用时）、耗时/用量、失败及最终产物。需明确敏感输入/输出的保留、脱敏、访问控制和日志策略；不要以保存完整内部推理文本作为可解释性的要求。

### 7. 首版架构保持模块清晰、部署简单

优先评估模块化单体，不因未来 A2A 或产品想象提前拆微服务。建议责任边界至少区分：角色包目录与导入导出、团队配置、协调/任务编排、角色运行时与模型适配、工具/知识连接器、运行记录/产物、前端工作区。落实方案应映射到当前仓库结构，说明旧 `agent/`、`RAG/` 和 `benchmark/` 的复用、保留、适配或隔离建议，避免未经论证整仓重写。

### 8. 为未来远程 Agent 留适配边界，但不先实现协议

内部执行接口应能表达“本地角色包运行”和“远程 Agent 执行器”这两类后端，但首版只实现本地角色。未来可评估 A2A；届时需另行设计远程身份/认证、能力声明信任、端点安全、用户数据披露、任务状态/取消、超时和交付物验证。MCP（工具/数据连接）与 A2A（Agent 间委派）职责不同，不要混为一个首版依赖。

## 首个端到端演示验收目标

使用一个真实但安全、范围不大的软件项目任务，完成以下可见流程：导入一个示例角色包；创建角色实例并加入团队；用户提交目标；协调者形成有限计划；角色读取获准的项目资料或调用 RAG/只读工具；根据工具结果继续、调整或说明受阻；交付带来源、假设和未决项的结构化产物；界面展示关键运行事件和最终状态。至少覆盖一个确定性失败场景（如工具超时或无权限），验证系统不会把失败伪装成成功或空结果。

验收关注产品机制和工程闭环：导入兼容性、成员权限边界、工具调用/反馈、任务状态、交付物和可追溯记录。不得把此验收扩展为该角色的专业水平认证。

## 要求协调 AI 输出的落实计划

只读检查仓库及相关 README、代码入口、测试、工作区状态后，在 `ai-work-orders/workspace/CURRENT.md` 指定的 `plan_path` 写出完整方案，并在协调对话中向用户总结。至少包括：

1. 对当前项目结构和未提交改动的影响判断；旧产品如何演进，是否需要新应用边界及推荐理由。
2. 模块职责、建议目录结构、模块间接口/数据契约；说明是逻辑模块还是部署服务。
3. 主要数据实体及关系；角色包 manifest/版本/导入导出格式建议。
4. 从首版到扩展版的阶段计划；每阶段目标、理由、负责边界、交付物、验收条件、针对性测试和停止条件。
5. 运行时任务/状态流转、协调策略、反馈/重试/暂停/取消/部分失败处理。
6. 工具/RAG/MCP/A2A 的当前与未来边界，凭据、最小权限、导入内容、提示注入和敏感日志风险的预防方案。
7. 前端核心页面/交互，以及如何演示过程而不是只展示最终文本。
8. 主要技术选型候选及适配当前仓库的取舍；优先沿用现有栈，指出不确定项，不为未来假设过度设计。
9. 测试与验收策略，区分产品功能正确性和角色专业能力评估；后者明确不在本项目范围。
10. 最大风险、依赖、实施顺序、需要用户决策的问题。

## 当前授权

当前只授权协调 AI 进行只读分析，并写入 `plan_path`。不得修改产品代码、配置、既有任务书，不得创建执行任务、提交或合并。方案完成后等待 Architect 和用户明确批准，不能把计划视为开发授权。
