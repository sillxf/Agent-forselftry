# RAG/agent demo findings

本文件记录构建“知识增强 Agent 架构顾问”时，通过实际调用当前本地 RAG 暴露出的能力问题。它不是产品运行数据，也不作为运行时输入。

## 2026-11-06 首次真实调用

### 1. 运行配置漂移

- `.env` 原来指向一个已撤销的只读 Key，且知识库 ID 已不存在于当前 `storage/catalog.sqlite3`。
- 本地管理台可以通过 loopback session 工作，但 Agent 是普通 REST 客户端，不能使用这个浏览器会话。
- 处理：为本地 demo 创建新的限定知识库只读 Key，并将当前知识库 ID 写回本地 `.env`。令牌不写入仓库、不打印、不提交。
- 改进建议：提供一个明确的 `agent doctor` 或 `python -m agent.demo --check`，启动前检查 URL、Key、知识库是否存在、是否已发布，并给出可操作错误；不要等到模型调用时才失败。

### 2. 默认检索可能返回主题相关但任务不相关的内容

- 用“重复登录失败/密码猜测”测试时，返回的是 Agent 面试文档里的子 Agent 推送、GRPO、LangGraph 等片段，而不是安全告警检测知识。
- 用“如何设计可靠 Agent 工作流”查询时，返回内容主题更吻合，但仍来自同一本混合型长 PDF，且结果包含面试题/回答语境。它可作为架构启发，不能直接视为当前项目需求的规范。
- 原因不是引用链断裂：每个结果都有 chunk/citation。问题是语义相关性与知识库范围没有表达“可信/适用/主题”边界。
- 改进建议：支持文档/标签/领域过滤；对 Agent demo 使用单独知识库或至少过滤指定来源；增加 query intent 与 source scope 的最小契约；在结果里显式区分“召回相关”与“适用证据”，不要让调用方把 top-k 当作事实集合。

### 3. CPU/重排配置导致首次查询延迟过高

- 一次 hybrid + reranker 查询实际约 89.5 秒；同一知识库用 `min_score` 且查询更短时约 0.45 秒，说明代价主要来自首次模型加载/重排或缓存状态，而非纯 HTTP。
- Agent demo 不应在没有延迟预算的情况下无条件调用高成本检索。当前 demo 已记录 `metadata.elapsed_ms`，并在没有通过相关性门槛的证据时跳过模型调用。
- 改进建议：把 embedding/reranker warm-up 状态和阶段耗时放入 trace；给调用方一个“快速检索/无重排”模式；在本地 demo 入口预热一次并显示进度；对超过预算的检索降级，而不是静默等待。

### 4. 证据存在不等于证据支持

- RAG 能返回有 citation 的文本，但不能判断该文本是否真的支持 Agent 的设计决策，也不能判断是否为最新版本/适用场景。
- demo 因此只允许模型声明 `reference_knowledge`、`supported_inference` 或 `unverified_hypothesis`，并对未知引用做代码降级；它不会把检索结果自动当作事实。
- 改进建议：后续增加小型答案级/设计级评测，至少标注“召回正确、适用、支持结论”三层，不用单一相似度替代证据质量。

## 本批次结论

先不改 RAG 核心排序算法。当前最有价值的工程闭环是：调用方传入多查询、使用相关性门槛、记录 trace、来源校验、无证据时拒绝生成。等有 20-30 条冻结的难题和人工标注后，再决定是否调整分块、模型或 reranker。
